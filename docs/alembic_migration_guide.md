# Alembic Migrations Guide

## Purpose

This document explains how CIIP will use Alembic for database migrations.

Alembic is responsible for versioning and applying database schema changes to PostgreSQL.

CIIP uses:

* FastAPI for the backend
* SQLAlchemy 2.0 for ORM models
* PostgreSQL as the database
* Alembic for migrations
* Docker Compose for local PostgreSQL
* macOS + VS Code for development

# Important Port Rules

PostgreSQL inside Docker listens on port:

```text
5432
```

On macOS, we expose it as:

```text
5434
```

The correct Docker Compose port mapping is:

```yaml
ports:
  - "5434:5432"
```

This means:

```text
FastAPI container → db:5432
Local macOS tools → localhost:5434
DBeaver → localhost:5434
Local Alembic from .venv → localhost:5434
```

The FastAPI container uses:

```env
DATABASE_URL=postgresql+psycopg://ciip_user:ciip_password@db:5432/ciip
```

Local Alembic, running from macOS `.venv`, uses:

```text
postgresql+psycopg://ciip_user:ciip_password@localhost:5434/ciip
```

# Will Alembic Delete Existing Data?

Normally, no.

Alembic migrations do not automatically delete table contents.

Safe operations usually include:

```text
create table
add nullable column
create index
create foreign key
create enum
add relationship table
```

Potentially destructive operations include:

```text
drop table
drop column
truncate table
delete from table
change column type without data conversion
rename column incorrectly
```

Alembic will only delete data if the migration file explicitly contains commands such as:

```python
op.drop_table("companies")
op.drop_column("companies", "name")
op.execute("DELETE FROM companies")
op.execute("TRUNCATE TABLE companies")
```

For this reason:

* always review autogenerated migration files before applying them
* never blindly apply migrations containing `drop_table`, `drop_column`, `DELETE`, or `TRUNCATE`
* use backups before destructive production migrations
* for local development, avoid deleting Docker volumes unless you want to reset the database

Important Docker warning:

```bash
docker compose down
```

Stops containers but keeps database data.

```bash
docker compose down -v
```

Stops containers and deletes Docker volumes, including PostgreSQL data.

Use `down -v` only when you intentionally want to reset the database.

# Step 3 — Initialize Alembic

Run Alembic initialization from the `backend/` folder, not the project root.

```bash
cd backend
alembic init alembic
```

This creates:

```text
backend/alembic/
backend/alembic.ini
```

If Alembic was accidentally initialized in the project root, remove the wrong files:

```bash
cd ..
rm -rf alembic alembic.ini
```

Then initialize correctly:

```bash
cd backend
alembic init alembic
```

If the command says:

```text
Directory alembic already exists
```

that means Alembic is already initialized. Do not initialize it again.

# Step 4 — Create SQLAlchemy Base

Create:

```text
backend/app/db/base.py
```

Content:

```python
from sqlalchemy.orm import DeclarativeBase


class Base(DeclarativeBase):
    pass
```

This `Base` will be used by all SQLAlchemy models.

---

# Step 5 — Create Models Package

Create:

```text
backend/app/models/__init__.py
```

At first this file can be empty.

Later, it will import all SQLAlchemy models so Alembic can detect them during autogeneration.

Example future content:

```python
from app.models.company import Company
from app.models.industry import Industry
from app.models.capability import Capability
from app.models.system import SystemApplication

__all__ = [
    "Company",
    "Industry",
    "Capability",
    "SystemApplication",
]
```

# Step 6 — Configure Alembic Database URL

Open:

```text
backend/alembic.ini
```

Find:

```ini
sqlalchemy.url = driver://user:pass@localhost/dbname
```

Replace with local macOS database URL:

```ini
sqlalchemy.url = postgresql+psycopg://ciip_user:ciip_password@localhost:5434/ciip
```

This allows Alembic to run from your local `.venv`.

Important:

Do not use `db:5432` in local Alembic.

`db:5432` only works inside Docker containers.

Use:

```text
localhost:5434
```

for macOS local tools.

# Step 7 — Connect Alembic to SQLAlchemy Metadata

Open:

```text
backend/alembic/env.py
```

Find:

```python
target_metadata = None
```

Replace it with:

```python
from app.db.base import Base

target_metadata = Base.metadata
```

The relevant section should look like:

```python
from logging.config import fileConfig

from sqlalchemy import engine_from_config
from sqlalchemy import pool

from alembic import context

from app.db.base import Base

target_metadata = Base.metadata
```

This allows Alembic to inspect SQLAlchemy models and generate migrations.

# Step 14 — How to Roll Back One Migration

To downgrade one migration:

```bash
cd backend
alembic downgrade -1
```

To upgrade again:

```bash
alembic upgrade head
```

Use downgrade carefully.

If a migration dropped a table or column, rollback may not restore data unless the migration explicitly handles it.

# Troubleshooting

## Problem: Port already in use

If port 5432 is already used by local PostgreSQL, use:

```yaml
ports:
  - "5434:5432"
```

Then connect locally through:

```text
localhost:5434
```

## Problem: Alembic cannot connect to `db`

This means you are running Alembic from macOS and using Docker hostname `db`.

Fix `backend/alembic.ini`:

```ini
sqlalchemy.url = postgresql+psycopg://ciip_user:ciip_password@localhost:5434/ciip
```

## Problem: FastAPI cannot connect to `localhost`

This means the FastAPI container is trying to connect to itself instead of the database container.

Fix `.env`:

```env
DATABASE_URL=postgresql+psycopg://ciip_user:ciip_password@db:5432/ciip
```

## Problem: Alembic autogenerate creates empty migration

Possible causes:

1. Models are not imported into Alembic metadata.
2. `target_metadata` is not set.
3. Models do not inherit from `Base`.
4. Models are not imported in `app/models/__init__.py`.

Fix later by ensuring:

```python
from app.db.base import Base
import app.models

target_metadata = Base.metadata
```

## Problem: DBeaver cannot connect

Check:

1. Docker database is running.
2. Port mapping is `5434:5432`.
3. DBeaver uses host `localhost`, port `5434`.
4. Database is `ciip`.
5. Username/password are correct.
6. No firewall or Docker issue.

# CIIP Migration Policy

1. Every schema change must have an Alembic migration.
2. Do not edit old migrations after they are pushed and used by others.
3. Create a new migration for new changes.
4. Review autogenerated migrations before applying.
5. Avoid destructive migrations unless necessary.
6. Document destructive migrations clearly.
7. Prefer additive changes in early development.
8. Keep migrations small and focused.
9. Test migrations locally before pushing.
10. Commit migration files with the model changes they support.
